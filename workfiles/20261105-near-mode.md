# Near Mode

> Working document — a search prefix (`n:` / `near:`) that selects the best match in the unfiltered grid instead of
> filtering it, so its neighbours stay one arrow key away.
> This file is the source of truth for the planned work until implemented,
> then the log of every adjustment made to it afterwards.

---

## Overview

Today, any text in the search box replaces the categories with one `Search results` section (`MainForm.OnSearchTextChanged`
→ `EmojiGrid.ShowSearchResults`), the tab strip greyed. The neighbours of an emoji — the other animals around 🐕 — are
gone.

**Near mode**: a search box text starting with `n:` or `near:` keeps the **category view** as it is, unfiltered, and
moves the **selection** onto the emoji the rest of the text finds — the best-ranked result of the normal search.
`n:chien` → the grid shows every category, 🐕 is selected and scrolled into view; ← / → then walk to the other
animals, Enter inserts whatever is selected.

Components touched:

| Component | Role |
|---|---|
| `Data/EmojiSearch.cs` | Recognises the prefix and gives the term (pure, testable) |
| `UI/MainForm.cs` | `OnSearchTextChanged` branches to near mode; `ProcessCmdKey` routes the arrows and F3 / Shift+F3 |
| `UI/EmojiGrid.cs` | Selects a given emoji in the category view and scrolls to it |
| `UI/EmojiDetailsPanel.cs` | Highlights the term, prefix left out |

---

## Prefix

- Near mode is on while the box's text **starts with** `n:` or `near:`; the **term** is what follows the prefix.
- **Lenient**: case ignored (`N:`, `Near:`), spaces before the prefix and after the colon ignored (`  n: chien` → term
  `chien`). A text without the prefix is a normal search, as today.
- The term is searched exactly as a normal search (`EmojiSearch.Find`, same keywords, symbols, characters, aliases,
  same ranking), over the same sections: the special characters while shown, then the catalog — never the frequent
  section nor the custom groups.

## Grid and Selection

- The grid **stays in the category view**: no `Search results` section, the sub-categories as set, the scroll
  position the categories had.
- On every change of the text, the selection goes to the **first match** of the ranking — its cell in the catalog's or
  the special characters' section, never a copy of it in the frequent section or a custom group — and the view scrolls
  to bring its **row to the middle of the viewport**, its neighbours above and below visible (clamped at the grid's
  top and bottom).
- **No match** (`n:xyzzy`), or an empty term (`n:`): the selection **stays where it is**, the grid does not move.
- **F3 / Shift+F3**: the next / previous match of the ranking, scrolled the same way. They **wrap around** (after the
  last, the first; before the first, the last) and answer **from the box and from the grid** alike, while near mode is
  on. They count from the last match jumped to, wherever the arrows moved the selection since. Outside near mode they
  do nothing.
- Enter / Ctrl+Enter insert the selection, as everywhere.

## Keyboard

- While near mode is on, the search box hands every **navigation key** to the grid at the first press, **as an empty
  box does** (`EmojiGrid.IsNavigationKey`): ← → ↑ ↓, Home / End, Ctrl+Home / Ctrl+End, Page Up / Page Down, Tab /
  Shift+Tab — from the selection, the grid taking the keyboard. The caret no longer moves in the text with them.
- A character or Backspace typed while the grid has the keyboard goes back to the box (unchanged): the term changes,
  the selection jumps to its new first match.

## Tab Strip and Details Panel

- The tab strip is **not greyed** — the categories are shown — and its active tab follows the scroll, as with an empty
  box.
- The details panel highlights the **term** (the prefix left out) in the selection's names and tags, as a normal search
  does.
- The cue banner stays `Search emojis`: near mode is not advertised in the box.

## Test Impact

The app has **no unit test project** (`src/` holds `EmojiSelector` only). The pure part — the prefix's recognition — is
checked by reflection on the built dll, as `RULES.md` describes for the other features; the grid and the keys by hand.

| Behaviour to pin | Test file | Create / Update |
|---|---|---|
| `n:` / `near:` recognised, the term extracted; other texts not near mode | None — reflection check on the dll | — |
| Selection on the first match, unfiltered grid, F3 / Shift+F3, arrows to the grid | None — checked by hand | — |

Chronological log of design refinements, of the choices the implementation run
took on its own — flagged `🧭 Implementation choices` — and of every adjustment
requested afterwards — flagged `⚙️ Post-implementation`. One entry per request,

### Iteration 1 — 2026-11-05

Initial design from the user's request (`n:` / `near:` selects without filtering; `n:chien` then ← / → to the other
animals) and the scoping batch (Q&A 1–4): navigation keys go straight to the grid, the best match is selected with
F3 / Shift+F3 to the next / previous one, no match leaves the selection alone. Exploration: one scout pass, done
directly — the questions chain (search → keyboard routing → grid selection). No row of `TODO-FEATURES.md` matches.

### Iteration 2 — 2026-11-05

Open Questions answered (Q&A 5): lenient prefix (case and spaces ignored); the match's row brought to the middle of
the viewport; F3 / Shift+F3 wrap around and answer from the box and the grid, counting from the last match jumped to
(a detail added here: the arrows moving the selection away do not reset it); tab strip not greyed, term highlighted,
matches in the catalog / special sections only — accepted; cue banner unchanged.
